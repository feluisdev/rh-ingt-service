## Project Overview

**RH-Service** is a Spring Boot microservice for Human Resources management, part of the SIGDI/SIPPROG platform for public administration in Cape Verde. It manages employees, departments, contracts, job positions, dependents, and qualifications.

- **Language:** Java 26
- **Framework:** Spring Boot 3.5.3 + Spring Cloud 2025.0.0
- **Architecture:** DDD + Hexagonal Architecture (Ports & Adapters) + CQRS
- **Database:** PostgreSQL 17 (JPA/Hibernate with Envers auditing)
- **Security:** OAuth2 + JWT via Keycloak (disabled in dev/staging)
- **File Storage:** MinIO (S3-compatible)
- **API Generation:** IGRP Studio (auto-generates REST controllers from JSON manifests)

## Architecture

### Module Structure

```
src/main/java/cv/igrp/RH_Service/
├── colaboradores/     # Core HR domain: Funcionario, Contrato, Dependente, Qualificacao, Documento, Assignment...
├── estrutura/         # Org structure: OrganizationalUnit ("Departamento"), Job ("Cargo"), Position, OrgFunction
├── carreiras/         # Career grid: Career, Category, Grade
├── parametrizacoes/   # Reference catalogs: Option, WorkerState, VinculoLaboral, ContractType, DocumentType, LeaveType, LeaveMobilitySubtype, PublicHoliday
├── recrutamento/      # Recruitment by concurso (Lei 20/X/2023 arts. 123–129): Concurso, Candidatura, ranking and provimento order
├── authorization/     # Authorization module (out of scope for HR domain work)
├── sigdi/             # SIGDI integration module (performance/evaluation)
└── shared/            # Cross-cutting: security, config, exceptions, pagination, Kafka
```

There is no `funcionarios/` package — despite the name used informally (and in `/docs/funcionarios/`) for this domain area, the actual HR domain code is split across `colaboradores`, `estrutura`, `carreiras` and `parametrizacoes` as above.

Dependency direction (leaves → top): `parametrizacoes`, `carreiras` (no outbound dependencies) ← `estrutura` ← `colaboradores`. The one exception is `estrutura/infrastructure/lookup/FuncionarioLookupAdapter.java`, the single file in `estrutura` authorized to import `colaboradores` (an anti-corruption-layer adapter behind `estrutura/application/port/FuncionarioLookupPort.java`); `colaboradores` importing `estrutura`/`parametrizacoes`/`carreiras` has no equivalent port/ACL restriction. `recrutamento` sits on top: it imports `colaboradores` (Funcionario, publicações), `estrutura` (Position, occupancy port) and `carreiras` (Category); nothing imports `recrutamento`.

Each module follows hexagonal layers:
- `interfaces/rest/` — REST controllers (auto-generated by IGRP Studio, do not edit directly)
- `application/` — Command/Query handlers, DTOs
- `domain/` — Pure domain models and business logic
- `infrastructure/` — JPA repositories and adapters

### Domain Identity Pattern

Each aggregate root has its own **typed identity value object** in `domain/valueobject/`. This is a DDD practice: the type system prevents passing the wrong ID to the wrong repository, makes intent explicit, and keeps `ExternalID` (the shared UUID wrapper) out of domain boundaries.

**Rule: never expose `ExternalID` in domain models, repository ports, adapters, or handlers.** Only the infrastructure layer (mapper) needs to know about it.

The value object is immutable, has no public constructor, and exposes only factory methods and read accessors:

```java
// domain/valueobject/AggregateId.java  ← one per aggregate root
public final class AggregateId {
    private final ExternalID valor;
    private AggregateId(ExternalID valor) { ... }

    public static AggregateId gerarNovo()         { return new AggregateId(ExternalID.gerarNovo()); }
    public static AggregateId from(UUID uuid)      { return new AggregateId(ExternalID.from(uuid)); }
    public static AggregateId from(String str)     { return new AggregateId(ExternalID.from(str)); }

    public UUID getValor()         { return valor.getValor(); }
    public String getStringValor() { return valor.getStringValor(); }
    // equals + hashCode delegate to valor
}
```

Each layer uses the typed ID naturally:

| Layer | Usage |
|---|---|
| Domain model | `private AggregateId id;` / factory uses `AggregateId.gerarNovo()` |
| Repository port | `Optional<Aggregate> findById(AggregateId id)` |
| Mapper `toDomain` | `AggregateId.from(entity.getId())` — the only bridge point |
| Mapper `toEntity` | `entity.setId(domain.getId().getValor())` |
| Handler | `AggregateId.from(command.getEntityId())` |

Canonical reference: `sigdi/domain/admin/valueobject/InstitutionId.java`. All `parametrizacoes` catalogs follow this pattern (`WorkerStateId`, `LeaveTypeId`, `OptionId`, etc.).

Note: this pattern governs an aggregate's *own* identity. References *between* aggregates are inconsistent in practice — some are typed (`carreiras.Category.careerId: CareerId`, `colaboradores.Documento.documentTypeId: DocumentTypeId`), others are raw `UUID` even within the same module (`estrutura.Position.jobId`, `colaboradores.Funcionario.workerStateId`). Only one raw-`UUID` case is documented as a deliberate cross-module decision (`OrganizationalUnit.responsibleEmployeeId`, citing a `D-09` note). Prefer the typed form for new cross-aggregate references unless there's a documented reason not to.

### CQRS & IGRP Framework

The project uses a custom IGRP framework (`cv.igrp.framework:core`) for command/query dispatching. Controllers are annotated with `@IgrpController`; handlers with `@IgrpCommandHandler`. Business logic lives in handlers — not controllers.

**Critical:** Controllers in `interfaces/rest/` are auto-generated from manifests in `.igrpstudio/` and are marked `/* THIS FILE WAS GENERATED AUTOMATICALLY */`. Regeneration overwrites them — keep business logic in handlers.

To add new endpoints or modules, use the `igrp-spring-generator` Claude Code skill. Manifests are stored under `.igrpstudio/<module>/` — see `.claude/skills/igrp-spring-generator/` for full reference.

### Security Profile Behavior

| Profile | Behavior |
|---|---|
| `development` / `staging` | All security disabled, CORS allow-all |
| `production` | OAuth2 Resource Server + Keycloak JWT enforcement |

Active profile is set via `SERVICE_PROFILE` env var. Never rely on security in dev for testing auth flows.

### Entity Auditing

Hibernate Envers is enabled. All audited entities track create/update timestamps and the acting user via `ApplicationAuditorAware` (reads from `SecurityContextHelper`).

### Scheduled Jobs

Background jobs use the framework in `shared/application/services/scheduler/` (ported from `inss_core_service`), not `@Scheduled`: implement `ScheduledJob` as a `@Component` and the `SchedulerService` seeds its config in `t_scheduler_job`, schedules it, and every run is logged in `t_scheduler_execucao` (manual trigger, re-run, missed-run detection, timeout, retry). REST under `/api/v1/rh/schedulers`. It is replica-safe (row lock on the job before opening a run) and every timestamp it stores is Cabo Verde local time (`RelogioScheduler`). Jobs run under the `SystemAuditor` author `scheduler:<chave>`. Derive the business date from `JobContext.dataReferencia()`, never `now()`. The five `sigdi` jobs are still plain `@Scheduled`.

## Key Domain Models

| Model | Module | Description |
|---|---|---|
| `Funcionario` | colaboradores | Employee aggregate root |
| `Contrato` | colaboradores | Employment contract |
| `Dependente` | colaboradores | Employee family dependent |
| `Qualificacao` | colaboradores | Professional qualification |
| `Documento` | colaboradores | Employee document |
| `Assignment` | colaboradores | Position/grade/function assignment |
| `Job` | estrutura | Job position with salary/hierarchy (informally "Cargo") |
| `OrganizationalUnit` | estrutura | Organizational unit (informally "Departamento") |
| `Position` | estrutura | A specific seat/slot in the staffing plan, distinct from `Job` |
| `OrgFunction` | estrutura | Organizational function |
| `Career` / `Category` / `Grade` | carreiras | Career grid |

| `Option` | parametrizacoes | Generic label catalog (ccode/ckey/cvalue/locale); `@Cacheable` on read, `@CacheEvict` on write (Caffeine, TTL 60 s) |
| `WorkerState` | parametrizacoes | Worker status catalog; `is_core=true` blocks deactivation (ACTIVE, INACTIVE are protected) |
| `VinculoLaboral` | parametrizacoes | Employment situation catalog (informally "ProfessionalSituation"); `countsSeniority`, `eligibleForProgression` |
| `ContractType` | parametrizacoes | Contract type catalog (per Decreto-Lei 4/2024) |
| `DocumentType` | parametrizacoes | Document type catalog; `allowed_extensions` (e.g. `pdf,docx`) + `category` (String holding an Option `DOC_CATEGORY` ckey — not an FK) |
| `LeaveType` | parametrizacoes | Leave type catalog; `deducts_balance`, `requires_approval`, `regime` (FERIAS/FALTA/FALTA_INJUSTIFICADA), `contagem` (DIAS_UTEIS/DIAS_SEGUIDOS), three day caps (year/occurrence/month), `max_minutos_por_dia`, `efeito_remuneracao`, `category` (String, Option `LEAVE_CATEGORY` ckey — not an FK) |
| `LeaveMobilitySubtype` | parametrizacoes | Mobility subtype; `record_type` ∈ {LICENCA, MOBILIDADE, AMBOS}; `affects_pay`, `counts_for_seniority`, `can_self_submit` |
| `PublicHoliday` | parametrizacoes | Institution holiday calendar; `is_recurring` (same day/month every year from the date's year) + optional `area_ckey` (Option `AREA_GEOGRAFICA`; the org unit says which area it is in). All active holidays count, not just national ones (V55). No DB unique index — one-active-national-per-day is application-only |

Shared value objects: `ExternalID` (UUID wrapper), `Estado` enum (ATIVO/INATIVO). Each domain aggregate has its own typed `XId` that wraps `ExternalID` — see Domain Identity Pattern above.
