O ciclo de vida do funcionário público, endpoint a endpoint

Para cada operação da API: o que faz, o contexto de negócio, que tabela afeta, e um exemplo real de pedido e resposta. Da regra à coluna e ao JSON.

29 tabelas RH 32 controllers prefixo api/v1/rh Java 23 · Spring Boot 3.5

O RH-Service gere o dossiê completo do funcionário público de Cabo Verde, no âmbito do SIPPROG (Sistema de Informação do Pessoal e Progressões) do INGT. Cobre todo o percurso — da admissão à cessação: identificação, contratos, enquadramento na grelha de carreiras (PCFR), colocação em unidades orgânicas, dependentes, habilitações, formações, processos disciplinares, ausências, licenças, mobilidades e recibos.

Orientação

Convenções

Prefixo: todos os caminhos começam por api/v1/rh/ (omitido nas fichas por brevidade). IDs: UUID. Datas: YYYY-MM-DD. Paginação: pagina (0-based) e tamanho. Soft delete: DELETE marca is_active = false; reativa-se com /activate. Campos *Desc/*Name nas respostas são labels legíveis derivados de catálogos.

O modelo mental

Quem é vs. o que lhe acontece

O funcionário sabe apenas quem é e em que estado laboral está. Tudo o que muda ao longo do tempo — contrato, carreira, unidade — vive em históricos separados, porque cada dimensão muda por uma razão diferente.

Funcionário ├── Histórico de Contratos ↳ muda com: renovação, mudança de tipo de contrato ├── Histórico de Enquadramentos ↳ muda com: promoção de escalão, mudança de cargo └── Histórico de Colocações ↳ muda com: mobilidade para outra unidade
Padrão is_current

Em cada histórico há um único registo ativo por funcionário. Ao criar um novo, o anterior fecha (is_current = false, end_date = nova_data − 1 dia) e o novo fica corrente. Esta lógica é feita no handler da aplicação, dentro de uma transação.

Como se guardam os catálogos

Os campos que apontam para t_option_entity guardam o ckey como texto (ex.: genero = "M"), não um UUID. Só o worker_state_id é uma FK de catálogo real no funcionário; os restantes catálogos de comportamento são FK UUID a partir dos históricos e sub-recursos.

Bloco 1 · Comportamento

Parametrizações com comportamento

1

Catálogos dedicados

/catalogs/*
Negócio

Estes catálogos têm tabela própria porque os seus campos alteram a lógica do sistema: um estado is_core não se apaga; um tipo de ausência com deducts_balance dispara validação de saldo; um tipo de contrato define se o enquadramento exige carreira. Todos têm CRUD completo sob /catalogs/ e a desativação é recusada (409) se estiverem em uso.

Bloco 2 · Estrutura

Estrutura organizacional

2

Unidades, cargos e funções

/estrutura/*
Negócio

As unidades orgânicas formam uma árvore (Direção → Departamento → Divisão → Secção). Os cargos são a designação oficial; as funções o papel efetivamente exercido. Cada função pode pertencer a um cargo (jobId): o funcionário com esse cargo herda todas as funções ligadas a ele; o functionId no enquadramento regista qual exerce. Ao registar o enquadramento, valida-se funcao.job_id == cargo_id (ou nulo) → senão 422.

Tabelas

t_unidade_organica (parent_unit_id, type, acronym) · t_job (code, nivel) · t_funcao (job_id nullable).

Bloco 3 · Carreiras

Carreiras e progressão (PCFR)

3

Carreira → Categoria → Escalão

/careers · /categories · /grades
Negócio

A grelha salarial do PCFR (DL 4/2024) é uma hierarquia rígida. Uma carreira agrupa categorias; cada categoria contém escalões. O escalão carrega o índice e o salário base; a categoria define a ordem_progressao. Não se cria categoria sem carreira, nem escalão sem categoria.

Tabelas

Bloco 7 · Ficheiros

Documentos — um sistema polimórfico

7

t_document

/funcionarios/{id}/documentos · aninhados
Negócio

Em vez de uma tabela de anexos por entidade, há uma única tabela genérica que se liga a qualquer registo através de reference_entity (a tabela) + reference_id (o UUID). O mesmo mecanismo serve o justificativo de uma ausência, o certificado de uma formação ou o diploma académico.

Onde fica o ficheiro

O ficheiro físico vive no MinIO (S3). A tabela guarda só a file_key; o download devolve uma URL pré-assinada — o ficheiro não passa pelo servidor. O fluxo é em duas etapas: (1) o frontend carrega o ficheiro para o MinIO; (2) regista os metadados na API (JSON, não multipart).

Tabela · t_document (polimórfica pura)

reference_entity · reference_id · document_type_id · file_key · original_filename · content_type · file_size. Sem funcionario_id.

Endpoints

Usa /leave-requests e /leaves-mobilities globais (o código usa sub-recursos aninhados), PUT /approve em inglês (o código usa PATCH /aprovar) e catálogos sem /catalogs/.

A Especificação diz "26 tabelas"; o Modelo Relacional diz "30 (29+1 IAM)". O código confirma 29 RH + 1 IAM.
