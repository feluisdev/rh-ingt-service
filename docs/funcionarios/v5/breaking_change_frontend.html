Breaking Changes — v5

Guia de migração do frontend para o modelo de Mapa de Pessoal (Lugares + Afectações). O que muda no contrato e nos ecrãs.

Documentação v5 · refactor Position Management · companion do api_guide.html
TL;DR
  1. O registo deixa de enviar unidade/cargo/carreira — envia positionId + gradeId.
  2. Enquadramento + Colocação → uma só Afectação (assignment).
  3. Novos ecrãs: gestão do Mapa de Pessoal e picker de Lugar vago.
  4. Novas queries: chefe, responsável, unidade-atual, vagas.
  5. Mobilidade exige destinationPositionId.

1.Registo de colaborador BREAKING

Antes

  • enviava unidadeOrganicaId, cargoId, careerId, categoryId
  • bloco enquadramento + bloco colocacao
  • resposta com enquadramentoId

Agora

  • envia só afectacao: { positionId, gradeId, origem, dataInicio }
  • unidade/cargo/carreira derivam do Lugar
  • resposta com afectacaoId
POST /api/v1/rh/funcionarios/registar
{
  "funcionario": { … },
  "contrato": { … },              // opcional
  "afectacao": { "positionId":"uuid", "gradeId":"uuid|null",
                 "origem":"ADMISSAO", "dataInicio":"YYYY-MM-DD" },
  "dadosBancarios": { … }         // opcional
}
// → 201 { funcionarioId, numeroFuncionario, contratoId, afectacaoId,
//         dadosBancariosId, documentoIds[], message }   // sem enquadramentoId
Ação FE: no ecrã de admissão, unidade/cargo/carreira/categoria passam a só-leitura, preenchidos a partir do Lugar selecionado.

2.Picker de Lugar vago (novo)

Para admitir, escolher um Lugar vago da unidade:

GET /api/v1/rh/colaboradores/assignments/unidade/{unidadeId}/vagas/lista
→ Lugares vagos com jobNome, unidadeNome, careerNome, categoryNome, foraDeGrelha
Filtrar o picker de escalões pela categoria do Lugar (grade.categoryId == position.categoryId) — a API ainda não valida no servidor.

3.Gestão do Mapa de Pessoal (novo ecrã)

AçãoEndpoint
Listar por unidade (+ vagas)GET /estrutura/positions?unidadeId={id}
CriarPOST /estrutura/positions

Chefias ao criar: parentPositionId (reporte) e managesUnitId (unidade dirigida). O card de unidade mostra dotação / ocupados / vagas.

5.Mobilidade BREAKING

// LicencaMobilidadeRequestDTO ganha:

Mobilidade com regresso ao Lugar de origem

  participant FE as Frontend
  participant API as RH-Service
  FE->>API: PUT /licencas-mobilidade/{id}/approve
  API-->>FE: 200 · afectação criada no Lugar de destino
  Note over API: Lugar de origem fica vago

6.Mudança de estado

PATCH /funcionarios/{id}/worker-state — request inalterado. Efeito novo: RETIRED/INACTIVE encerram a afectação corrente → o Lugar volta a vago.

7.Endpoints removidos / substituídos

RemovidoUsar
/funcionarios/{id}/enquadramentos/colaboradores/assignments
/funcionarios/{id}/colocacoes/colaboradores/assignments
audit catálogo enquadramentosaudit catálogo assignments
O bloco enquadramento ainda aparece em GET /funcionarios/{id}/details (mesma forma, por compat) — mas é derivado do Lugar. Não há CRUD de enquadramento.

8.Checklist de migração FE

  • Ecrã de admissão: remover inputs de unidade/cargo/carreira; adicionar picker de Lugar vago + escalão.
  • Ler afectacaoId (em vez de enquadramentoId) na resposta de registo.
  • Novo ecrã de gestão do Mapa de Pessoal (Lugares + chefias + vagas).
  • Mobilidade: adicionar campo destinationPositionId.
  • Remover chamadas a /enquadramentos e /colocacoes.
  • Usar as novas queries (unidade-atual, chefe, responsavel, vagas).
  • Enviar Accept: application/json em todas as chamadas.
