## 1. Arquitetura e Padrões de Implementação

O projeto adota a arquitetura **IGRP Next.js** baseada em *Feature-Sliced Design* adaptado, onde cada módulo de negócio possui suas próprias rotas, controladores e serviços.

### 1.1. Estrutura de Pastas (Convenção)
```text
src/
├── app/
│   ├── (igrp)/                     # Layout Autenticado (Sidebar, Header)
│   │   ├── strategy/
│   │   │   ├── map/page.tsx        # Página Mapa Estratégico
│   │   │   └── identity/page.tsx   # Página Identidade
│   │   ├── tactical/
│   │   │   ├── paa/
│   │   │   │   ├── list/page.tsx   # Listagem PAA
│   │   │   │   └── new/page.tsx    # Wizard Criação
│   │   └── layout.tsx              # IGRPRootLayout
│   ├── (sigdi)/                    # Camada de Lógica (Business Layer)
│   │   ├── hooks/controllers/      # ViewModels (1 por Page)
│   │   ├── services/               # Clients HTTP (1 por Módulo)
│   │   └── types/                  # DTOs e Interfaces
│   └── api/                        # Route Handlers (Proxy/BFF)
├── components/
│   ├── common/                     # UI Kit (Buttons, Inputs, Cards)
│   ├── strategy/                   # Componentes específicos de Estratégia
│   └── tactical/                   # Componentes específicos de Tático
```

### 1.2. Padrão de Página (Page Pattern)
Todas as páginas devem seguir estritamente o padrão **Container/Presenter** via Hooks:

**`src/app/(igrp)/module/page.tsx` (The View):**
```tsx
export default function Page() {
  const { state, actions } = useModuleController();
  
  if (state.isLoading) return <SkeletonPage />;
  
  return (
    <ModuleTemplate 
      data={state.data} 
      onAction={actions.handleAction} 
    />
  );
}
```

**`src/app/(sigdi)/hooks/controllers/useModuleController.ts` (The Logic):**
```ts
export function useModuleController() {
  const { data, isLoading } = useQuery(...); // React Query
  const mutation = useMutation(...);
  
  const handleAction = () => { ... };
  
  return { state: { data, isLoading }, actions: { handleAction } };
}
```

## 2. Especificação Detalhada de Páginas por Módulo

### 2.1. Módulo Estratégico (Strategy)

#### Página: Mapa Estratégico (BSC)
*   **Rota:** `/app/(igrp)/strategy/map/page.tsx`
*   **Objetivo:** Visualizar e editar o grafo de objetivos estratégicos e suas relações de causa-efeito.
*   **Controller:** `useStrategyMapController`
*   **Dependências de Dados:**
    *   Query: `GET /v1/strategy/map/current` (Key: `['strategy-map']`)
    *   Mutation: `POST /v1/strategy/map/links` (Cria aresta)
*   **Componentes:**
    *   `StrategicMapCanvas` (Smart): Wrapper do **React Flow**.
    *   `PerspectiveLane` (Dumb): Renderiza as raias (Financeira, Clientes, etc.).
    *   `GoalNode` (Dumb): Nó customizado com Título, KPI Sparkline e Status.
*   **Interações:**
    *   *Drag-and-drop:* Arrastar handle de um nó para outro cria link.
    *   *Click:* Abre `GoalDetailsDrawer`.
*   **Requisitos Específicos:**
    *   **Performance:** Renderizar até 100 nós sem lag (usar `memo` nos nós).
    *   **Acessibilidade:** Navegação por teclado entre nós (Tab/Arrow Keys) suportada pelo React Flow.

#### Página: Identidade Institucional
*   **Rota:** `/app/(igrp)/strategy/identity/page.tsx`
*   **Objetivo:** Editar Missão, Visão e Valores com versionamento.
*   **Controller:** `useIdentityController`
*   **Dependências de Dados:**
    *   Query: `GET /v1/strategy/identities/current`
    *   Mutation: `POST /v1/strategy/identities` (Novo Snapshot)
*   **Componentes:**
    *   `IdentityForm`: Formulário com `RichTextEditor` (TipTap ou Quill).
    *   `VersionHistorySidebar`: Lista lateral com versões anteriores.
*   **Validação (Zod):**
    *   `mission`: min(10 chars).
    *   `values`: min(1 item).

### 2.2. Módulo Tático (Tactical)

#### Página: Listagem do PAA (Plano Anual de Atividades)
*   **Rota:** `/app/(igrp)/tactical/paa/list/page.tsx`
*   **Objetivo:** Listar atividades com filtros avançados e exportação.
*   **Controller:** `usePaaListController`
*   **Dependências de Dados:**
    *   Query: `GET /v1/tactical/activities` (Params: `page`, `status`, `unit`)
*   **Componentes:**
    *   `GenericListPage`: Layout padrão IGRP.
    *   `ActivityFilters`: Inputs de busca, Select de Status e DataRangePicker.
    *   `ActivityListColumns`: Definição das colunas (Titulo, Orçamento, Status).
*   **Estados:**
    *   `filterState`: { term: string, status: string, dates: { from, to } }
    *   `pagination`: { page: 1, size: 20 }

#### Página: Wizard de Nova Atividade (5W2H)
*   **Rota:** `/app/(igrp)/tactical/paa/new/page.tsx`
*   **Objetivo:** Guiar o usuário na criação de uma atividade complexa.
*   **Controller:** `useActivityWizardController`
*   **Gerenciamento de Estado:** `Zustand` (Global Store para o Wizard) para persistir dados entre passos.
*   **Passos (IGRPStepper):**
    1.  **Vínculo Estratégico:** Select com busca de Objetivos Pais.
    2.  **Detalhamento (5W2H):** Formulário principal (O quê, Quem, Quando).
    3.  **Orçamento:** Integração com Calculadora Driver-Based.
    4.  **Revisão:** Resumo readonly antes do submit.
*   **Integrações Críticas:**
    *   No passo 3, chamar `POST /v1/budget/calculator/simulate` a cada alteração de inputs de custo.
    *   Exibir `BudgetStatusBadge` (Verde/Vermelho) baseado na resposta.

## 3. Especificações Técnicas Transversais

### 3.1. Requisitos de Formulários
*   **Biblioteca:** `React Hook Form` + `Zod Resolver`.
*   **Validação:** Schema-first. Todas as regras de negócio de UI (ex: Data Fim >= Data Início) devem estar no schema Zod.
*   **Feedback:** Erros devem aparecer abaixo do input (`FormMessage`) e o input deve ter borda vermelha (`border-destructive`).

### 3.2. Tratamento de Erros (Error Boundaries)
*   **Global:** `src/app/(igrp)/error.tsx` captura falhas não tratadas e exibe tela "Algo correu mal" com botão "Tentar Novamente".
*   **Local:** Componentes críticos (como `StrategicMapCanvas`) devem ser envolvidos em `ErrorBoundary` próprio para não quebrar a página toda se o grafo falhar.

### 3.3. Acessibilidade (WCAG 2.1 AA)
*   **Foco:** O Wizard deve gerenciar o foco ao trocar de passo (focar no primeiro input do novo passo).
*   **Cores:** Todos os textos de status (Badges) devem ter contraste > 4.5:1.
    *   *Errado:* Texto branco em fundo amarelo claro.
    *   *Correto:* Texto preto/escuro em fundo amarelo (`bg-yellow-100 text-yellow-800`).
*   **Leitores de Tela:** Gráficos (Recharts) devem ter tabela de dados alternativa ou descrição `aria-label` detalhada.

### 3.4. Testes Unitários (Critérios Mínimos)
Cada página deve ter um arquivo de teste correspondente `page.test.tsx` verificando:
1.  **Smoke Test:** A página renderiza sem erros?
2.  **Loading State:** Exibe Skeleton enquanto carrega?
3.  **Error State:** Exibe mensagem amigável se API falhar?
4.  **Interaction:** O botão de submit chama a função correta?

## 4. Integração com Backend (API Contracts)

Os serviços frontend (`src/app/(sigdi)/services/*`) devem implementar estritamente os contratos definidos na **Spec Técnica Backend v4.0**:

| Serviço Frontend | Método | Endpoint Backend | Contrato (Payload) |
| :--- | :--- | :--- | :--- |
| `StrategyService` | `createGoal` | `POST /v1/strategy/goals` | `{ title, perspective }` |
| `TacticalService` | `createActivity` | `POST /v1/tactical/activities` | `{ strategicGoalId, budget: {...} }` |
| `BudgetService` | `simulate` | `POST /v1/budget/calculator/simulate` | `{ driverType, params }` |

**Nota:** O Frontend **NÃO** deve realizar cálculos de negócio críticos (ex: cálculo de imposto ou validação final de saldo). Deve sempre consultar a API (Server-Side Validation).
